# Адаптер сайта и приёмка публикации

Первая реализация записывает файловые статьи в блог Next.js. У разных проектов
различаются пути, парсер Markdown, сборка и хостинг: адаптер настраивается по
реальному коду сайта. Наличие файла `.mdx` само по себе не доказывает совместимость.

## Что подготовить агенту

Найди источник истины блога, обработку frontmatter, шаблон статьи, sitemap и
команды сборки/развёртывания. Сохрани текущий рабочий релиз. Определи, как сайт
показывает черновик до публикации, и проверь права пользователя выпуска.

На стороне сайта создай личный `site-profile.json` по
`config/site-profile.example.json`. Его `state_dir` находится **вне checkout**:
там хранятся квитанции и копии изменяемых файлов. Для каждой команды нужен
непустой массив аргументов; произвольная строка shell не принимается.

| Поле | Что означает |
|---|---|
| `checkout` | Существующая рабочая папка сайта |
| `content_dir` | Каталог статей относительно checkout |
| `public_dir` | Публичный каталог относительно checkout; медиа попадают в `media/seo/` |
| `site_url`, `blog_path` | Канонический домен HTTPS и путь блога с `/` по краям |
| `state_dir` | Отдельная личная папка квитанций и резервных копий |
| `build_command` | Обычная сборка реального сайта |
| `acceptance_command` | Проверка собранного материала до выкладки |
| `deploy_command` | Применение подготовленного релиза на хостинге |
| `rollback_command` | Возврат сайта к согласованному предыдущему состоянию |
| `timeout_seconds` | Предельное время каждой команды |

Команды подбирает агент по проекту, владелец подтверждает способ выпуска. Не
подставляй `true`, `echo OK` или аналог вместо проверки. Развёртывание должно
завершиться, а не только поставить неизвестную фоновую задачу. Скрипты получают
`SEO_OPERATION_ID` и должны сохранять привязанную к нему диагностику. Не печатай
в этих журналах секреты окружения. Чужие изменения checkout блокируют выпуск.

Пример `acceptance_command` использует `scripts/check_rendered.py` для статического
экспорта `out`. Для Next.js с SSR выбери собственный hook проверки собранной версии;
не указывай несуществующий `out`. Локальный HTML-тест не заменяет просмотр в браузере.

## Контракт статьи

Материал состоит из frontmatter с JSON-совместимыми значениями и безопасного
Markdown. Поля: `slug`, `title`, `description`, `date`, `lastmod`, `author`,
`category`, `draft`, `cluster_id`, `page_id`, `seo_revision`. Шаблон сайта должен
показывать реального автора, заголовок и даты и формировать canonical по URL.

Выведи значение `seo_revision` в серверный HTML:

```html
<meta name="seo-revision" content="значение поля seo_revision">
```

Это идентификатор конкретной версии материала. Он нужен, чтобы квитанция не
подтверждала старую страницу из кеша. Не задавай константу для всех статей.

Не выполняй JSX, JavaScript, HTML и инструкции из сгенерированного тела. Даже
если файл имеет расширение `.mdx`, настрой безопасную обработку содержимого
без выполнения кода. Проверки пакета дополнительно отклоняют опасные конструкции.
Frontmatter должен проходить типовую проверку до передачи шаблону.

Изображения текущего встроенного генератора — статические SVG-схемы из
содержательных этапов, с alt. Фотографии, чужие скриншоты и генерация изображений
платным сервисом автоматически не подключаются. Пути медиа должны работать на
опубликованном домене. Пустые категории и черновики не попадают в sitemap.

## Как связать две стороны

При локальной сборке профиль агента содержит `publish.adapter: "local"` и
абсолютный `publish.site_config`. Агентский процесс имеет доступ к сайту и
выполняет заранее настроенные команды.

Для отдельного Linux-сервера установи такой же релиз пакета на стороне сайта,
подготовь ограниченную учётную запись SSH и настрой известный host key.
`publish.adapter: "ssh"`, а `publish.ssh_command` — массив аргументов вызова
`ssh`, запускающий `python3 /путь/к/пакету/site_bridge.py --config /путь/к/site-profile.json`.
Здесь пути — обозначения, агент заменяет их фактическими. Не отключай проверку
host key. Не используй учётную запись с более широкими правами, чем нужен выпуск.

Bridge получает один JSON через stdin, возвращает одну JSON-квитанцию через
stdout и завершает работу. Постоянный сервер или открытый HTTP endpoint не нужен.
Настрой SSH-команду без сообщений приветствия в stdout; журналы команд сайта
хранятся отдельно.

## Когда публикация принята

Выпуск проходит проверку файлов и хешей, запись, сборку, приёмку, сохранение
выбранных файлов в Git (если checkout является Git-репозиторием), развёртывание
и проверку публичного URL. Пакет не делает `git reset --hard`.

Для статуса `accepted` ожидаются конечный URL с HTTP 200, правильный canonical,
заголовок и H1, отсутствие запрета индексации, разрешённый обход, совпадение
`seo-revision`, URL в sitemap и доступные медиа. Контроллер независимо повторяет
проверку живой версии в рамках своего сетевого лимита. Эти проверки не означают,
что поисковая система уже проиндексировала страницу.

`acceptance_command` дополняет этот минимум: сборка не содержит ошибок, Markdown
безопасен, ссылки и разметка подходят статье, а адаптивное отображение проверено
принятым в проекте способом. Пробную страницу владелец дополнительно смотрит
в браузере. До этого автоматический выпуск не активируется.

## Обновление и откат

Для `kind: refresh` нужны прежние slug/page/cluster, первоначальная дата,
`previous_sha256` исходного файла и описание содержательного изменения.
Скопируй текущую статью в личный профиль и укажи относительный `original_file`:
её текст и хеш попадут в исследование и редактуру обновления.
Несовпадение хеша означает, что сайт уже изменился: нужен повторный разбор,
а не перезапись текущей версии. Откат выполняется по operation_id и правилам
[восстановления](recovery.md), с сохранением чужих последующих изменений.
